=================================================
I am working on an academic/engineering project about improving RAG retrieval when technical and colloquial/customer-support data are mixed together.

IMPORTANT: Treat me as a COMPLETE BEGINNER. Explain everything like I am a Class 1 student. Do not assume I know Python, embeddings, vector databases, RAG, LangChain, ontology, taxonomy, semantic search, etc. Whenever you introduce a technical term, explain it first in very simple language with a real-life example.

1. CORE PROBLEM

I have two types of text data:

Colloquial / Customer Data

Examples:

"i need help to find out why my account is blocked"
"can you check what happened with my payment? i see an error"
"why is there an extra charge on my invoice, please fix this"
Technical Data

Examples:

"System database connection timeout during data migration script execution. JDBC driver throws network error."
"API gateway authentication handshake failure due to expired SSL token on router endpoint."
"Server cluster resource allocation threshold exceeded. Kubernetes pod restarting automatically due to memory leaks."

The problem is that both datasets are stored/retrieved together.

A user might ask:

"My account has a connection error, why?"

A naive vector/semantic search may retrieve:

"System database connection timeout during data migration script execution. JDBC driver throws network error."

instead of a customer-friendly document.

The reason is that words such as "connection" and "error" occur in both technical and colloquial contexts.

The goal is to prevent technical documents from contaminating retrieval for a normal customer query.

2. MAIN IDEA

We want to compare three different architectures:

PROJECT 1 — Metadata Filtering RAG

Basic architecture:

User Query
→ Query Classification
→ Metadata Filter
→ Semantic/Vector Search
→ Relevant Chunks
→ LLM
→ Answer

Each document receives metadata such as:

{
"audience": "colloquial",
"domain": "account",
"intent": "account_problem"
}

or:

{
"audience": "technical",
"domain": "database",
"intent": "connection_failure"
}

If the query is classified as colloquial, we filter:

audience = "colloquial"

Then semantic search only searches the allowed documents.

This is the simplest and cleanest architecture.

PROJECT 2 — Taxonomy + Ontology RAG

We also want to build a structured knowledge layer.

Taxonomy means categories.

Example:

Customer
├── Account
├── Payment
├── Invoice
└── Subscription

Technical
├── Database
├── Network
├── API
├── Kubernetes
└── Security

Ontology means relationships between concepts.

Example:

Customer
→ hasAccount
→ Account
→ hasProblem
→ Account Failure

Technical example:

Application
→ connectsTo
→ Database
→ hasProblem
→ Connection Timeout

The purpose is to help the system understand concepts and relationships, rather than only relying on word/vector similarity.

PROJECT 3 — HYBRID RAG

This is the advanced/final architecture.

It combines:

Taxonomy
+
Ontology
+
Metadata Filtering
+
Semantic/Vector Search
+
LLM

Conceptually:

USER QUERY
↓
Query Understanding
↓
Taxonomy Classification
↓
Ontology/Relationship Understanding
↓
Metadata Filtering
↓
Semantic Vector Search
↓
Relevant Chunks
↓
LLM
↓
Answer

The hypothesis is that combining structured knowledge with semantic retrieval can reduce incorrect retrieval caused by overlapping technical and colloquial vocabulary.

3. IMPORTANT CONCEPTS I HAVE ALREADY LEARNED

Explain these concepts again whenever needed, but keep them beginner-friendly.

Metadata

Extra information attached to a document.

Example:

text = "My account is blocked"
audience = colloquial
domain = account
intent = account_problem

Metadata Filter

A rule that says which documents are allowed into the search.

Example:

audience = colloquial

means technical documents are excluded from the search.

Embedding

Converting text into numbers that represent its meaning.

Example:

"My account is blocked"
→ [numbers...]

Vector

The numerical representation produced by an embedding model.

Vector Search

Searching through vectors to find semantically similar information.

Similarity Search

Finding which stored vectors are most similar/closest to the query vector.

Semantic Search

Search based more on meaning than exact keyword matching.

Example:

Query:
"I cannot access my account"

Document:
"My account is blocked"

Different words, but similar meaning.

Chunk

A small piece of a larger document.

Example:

100-page document
→ Chunk 1
→ Chunk 2
→ Chunk 3
...

Relevant Chunk

The chunk that contains information useful for answering the user's query.

RAG

Retrieval-Augmented Generation.

Simple flow:

User Question
→ Retrieve useful information
→ Give information to LLM
→ LLM generates answer

LangChain

A framework/toolkit that helps connect different parts of an LLM/RAG application.

It is NOT the embedding model, NOT the vector database, and NOT the LLM itself.
